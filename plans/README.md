## Key findings from recon (folded into plan 001, recorded here so they aren't re-derived)

- **`encryptSign()` is unrelated to the machine handshake.** It's called from
  `sources/b/b/a/a/g/c/d.java:1855` and `:1890`, both inside HTTP login/ping
  calls to `http://cutter.skycut.cn/v1/api/ver01/login` — a vendor cloud
  billing/licensing check, not the local serial protocol. Only
  `getHandshake(long)` is used for the on-device handshake
  (`RCMD=10,0;<nonce>` → `getHandshake(nonce)` → raw bytes written to the
  serial port). Building the bridge only needs `getHandshake`; `encryptSign`
  and `cmd_GetPassWordCutChar` can be exposed too (cheap to add) but are not
  required for the cutting flow.
- **The 3 sensitive natives are NOT plain exported ELF symbols.** Checked via
  `readelf -W --dyn-syms libnewcutjni.so`: only
  `Java_com_cut_cutjni_JniUtils_convertNumber` and `...convertNumber2` are
  statically exported. `getHandshake`, `encryptSign`, and
  `cmd_GetPassWordCutChar` are absent from the dynamic symbol table — they
  must be bound at runtime inside `JNI_OnLoad` (offset `0x15fd5`, present)
  via `RegisterNatives()`. **This rules out a bare C `dlopen`+`dlsym` bridge**
  (the approach originally sketched in the RE notes) — there is no plain
  symbol to `dlsym`. The native functions only become callable through a real
  `JNIEnv*` from a running ART/Dalvik VM that has loaded a class named exactly
  `com.cut.cutjni.JniUtils` with matching native method signatures. Plan 001
  uses `app_process` (stock Android technique) to get that real JNIEnv
  cheaply, instead of hand-rolling a fake JNI environment in C — much lower
  risk and no ELF reverse-engineering required.
- **The response bytes from `getHandshake()` are written to the serial port
  verbatim**, not wrapped in `RCMD=...;` text. Confirmed in
  `sources/cn/upus/app/upprinting/base/BaseDataBindingActivity.java:291-294`
  → `b.b.a.a.j.d` (`SerialPortHelp`) → `d.g(byte[])` at
  `sources/b/b/a/a/j/d.java:300-315`, which does `outputStream.write(bArr)`
  directly. The bridge's TCP response should hand back exactly the bytes
  `getHandshake()` returns (hex-encoded for the wire), with no framing added.
- **Physical-layer gap, not addressed by this plan**: `/dev/ttyS1` is internal
  to the board. For a PC-side replacement client to ever talk `RCMD=...` in
  real time (not just the handshake step), the PC needs its own electrical
  path onto that same UART — most plausibly by tapping the `UART0` header
  already identified on the board with a 3.3V USB-TTL adapter, while ensuring
  the stock Upprinting app / Android side is not simultaneously driving the
  same lines. This hasn't been verified against the schematic or continuity-
  tested, and is out of scope for plan 001. Flagging it here so it isn't
  forgotten before a "PC talks RCMD directly" plan is written.

## Execution log (2026-07-01, this session)

Plan 001 was executed live against the physical machine. Progress and the
current blocker, in order:

1. **Root confirmed working**: `adb devices` showed the device
   (`6S9OZFRLDN`), and `adbd` was already running as root (no `su -c` needed
   — plain `adb root` / `adb shell id` returns `uid=0`). Note: `su -c <cmd>`
   syntax itself fails on this device (`su: invalid uid/gid '-c'` — this
   build's `su` doesn't support the Chainfire/Magisk-style `-c` flag; just
   run commands directly, root is already the adb shell's uid).
2. **DEX toolchain**: no Android SDK / `d8`/`dx` was installed on this PC.
   Fetched the standalone D8 compiler as a plain jar from Google's Maven
   (`https://dl.google.com/dl/android/maven2/com/android/tools/r8/9.1.31/r8-9.1.31.jar`,
   ~19MB) instead of the full SDK — works via
   `java -cp r8.jar com.android.tools.r8.D8 ...`. Must be invoked with a
   JDK ≥ 9 `java.exe` explicitly (this machine's `java` on `PATH` resolves to
   an old JRE 8 first; the JDK 17 install lives at
   `C:\Program Files\Eclipse Adoptium\jdk-17.0.19.10-hotspot\bin\`).
3. **Bridge.java + cloned JniUtils.java compiled and dexed successfully.**
4. **First on-device run crashed immediately**: `System.loadLibrary("newcutjni")`
   via `java.library.path=/data/local/tmp` failed —
   `UnsatisfiedLinkError: dlopen failed: library "libcrypto.so" not found`.
   Fix: the original APK bundles its own `libcrypto.so`/`libssl.so` right
   next to `libnewcutjni.so` in `resources/lib/armeabi-v7a/` — these are
   NOT the system's BoringSSL libs. Pushed both to `/data/local/tmp/`.
5. **Setting `LD_LIBRARY_PATH=/data/local/tmp` globally for `app_process`
   broke ART's own bootstrap** — the runtime's own `libjavacore.so` picked up
   our bundled `libcrypto.so` instead of the system one and aborted with
   `LoadNativeLibrary failed for "libjavacore.so": dlopen failed: cannot
   locate symbol "BN_num_bytes"`. **Do not set `LD_LIBRARY_PATH` for the
   whole process.** Fixed by changing the cloned `JniUtils`'s static
   initializer to explicit, absolute-path `System.load()` calls in dependency
   order (`libcrypto.so` → `libssl.so` → `libnewcutjni.so`) instead of
   `System.loadLibrary` + `java.library.path`. This is a deliberate, justified
   deviation from the plan's literal Step 3 (which said to match the original
   class "exactly") — the static initializer's *loading mechanism* doesn't
   affect `RegisterNatives` binding, which only cares about class/method
   name and signature.
6. **Second crash, past library loading**: `JNI_OnLoad` itself aborts with
   `JNI DETECTED ERROR IN APPLICATION: java_object == null` inside a
   `GetObjectClass` call — i.e. the native init code expects a real Android
   `Context`/`Application` object and gets `null`, because a bare
   `app_process` main() has no Activity/Application lifecycle. **Fixed** by
   fabricating one via reflection before touching `JniUtils`:
   `Looper.prepareMainLooper()` then
   `ActivityThread.systemMain()` → `getSystemContext()`. This produces a
   real, non-null `android.app.ContextImpl` (package `android`, i.e. a
   *system* context, not `cn.upus.app.upprinting`'s own) and the null-deref
   abort stopped happening.
7. **Current blocker**: past that point, the native android log tag `qaz`
   prints `class have find` (from inside `libnewcutjni.so`, presumably after
   locating some expected class via `FindClass`), and the **process then
   dies with no further output and no debuggerd tombstone at all** — no
   `SIGABRT`/`SIGSEGV` entry appears in `logcat`, and no OOM-killer entry
   appears in `dmesg` either, across three repeated attempts. The consistent
   *absence* of a tombstone is itself the signal: debuggerd can report
   `SIGABRT`/`SIGSEGV` (as it did for finding #6 above, with a full
   backtrace) but **cannot** report `SIGKILL` — it's not an interceptable
   signal. This is consistent with the native code performing its own
   integrity/environment check after `FindClass` succeeds (plausibly
   checking `Context.getPackageName()` or similar against the expected
   `cn.upus.app.upprinting`, which our fabricated *system* context fails)
   and then calling something equivalent to `kill(getpid(), SIGKILL)`
   directly, bypassing any Java-catchable exception. This is inference, not
   confirmed by disassembly — recorded here as the leading hypothesis, not
   a fact.

**Where this leaves plan 001**: the bridge successfully loads the real
native library and gets past the Context-existence check, but does not yet
survive far enough to call `getHandshake` — something checked right after
`FindClass`/"class have find" causes a silent self-kill. Two candidate next
steps, not yet attempted:
- Fabricate a `Context` with `getPackageName()` (and ideally
  `getApplicationInfo()`) actually returning `cn.upus.app.upprinting`,
  rather than accepting `ActivityThread.getSystemContext()`'s `android`
  identity as-is — e.g. by wrapping/proxying `getPackageName()`, or by
  attempting a full package-context creation
  (`context.createPackageContext("cn.upus.app.upprinting", flags)`) if the
  package is installed at `/system/app/Upprinting/`.
- Abandon the standalone `app_process` approach and instead run this same
  probe code *inside* the real, already-running `cn.upus.app.upprinting`
  process (e.g. via Frida `Java.perform`), which already has a fully genuine
  `Context`/package identity and has already passed whatever check this is.

8. **Attempted fix, ruled out**: tried `systemContext.createPackageContext("cn.upus.app.upprinting", CONTEXT_INCLUDE_CODE | CONTEXT_IGNORE_SECURITY)` to get a `Context` whose `getPackageName()` correctly returns `cn.upus.app.upprinting` (confirmed in the bridge's own stdout — it also resolved the real classloader:
   `PathClassLoader[... zip file "/system/app/Upprinting/Upprinting.apk" ...]`), and set it as the thread's context classloader. **No change in outcome** — the process still dies silently at the same point, same ~2s timing, with no tombstone, immediately after `class have find`. This rules out the simple version of the hypothesis in #7: the native code is not reading *our* Java-level `Context` object at all (we never touched it beyond creating a local variable), so whatever check is failing must be reading Android's own internal state directly (e.g. a static `ActivityThread`/`AppGlobals` field we didn't modify) — or the check isn't about package identity at all. The consistent ~2 second delay from `Calling main entry Bridge` to `class have find` to death, reproducible across all three attempts, is itself a clue worth carrying forward: it reads more like a timer/watchdog (e.g. "self-destruct if some expected follow-up call doesn't happen within N seconds of `JNI_OnLoad` completing") than an instantaneous identity check — but this is still inference, not confirmed.

**Conclusion for this session**: further progress needs actual disassembly of
`libnewcutjni.so` around the code that runs just after the `"qaz"/"class have
find"` log call in `JNI_OnLoad` (offset `0x160d3` is where `JNI_OnLoad`
resumes after that logging point — a Ghidra/IDA session focused specifically
on that address range, not the whole binary, is the efficient next step) to
see what it actually checks and how it kills the process, rather than more
blind Java-side Context experiments. The alternative path — running this
same probe inside the real, already-running `cn.upus.app.upprinting` process
via Frida instead of a bare `app_process` — sidesteps needing to understand
the check at all, since a genuinely-running instance of the real app has
already satisfied it once.

9. **Switched approach to Frida (injecting into the real running process)**,
   per operator decision. Setup, all confirmed working:
   - Installed `frida-tools`/`frida` (client, v17.15.3) on the PC via `pip`.
   - Downloaded the matching `frida-server-17.15.3-android-arm.xz` from
     `https://github.com/frida/frida/releases/download/17.15.3/frida-server-17.15.3-android-arm.xz`,
     decompressed (plain LZMA, `python -m lzma` works, no `xz` binary
     needed), pushed to `/data/local/tmp/frida-server`, `chmod 755`, ran as
     root with `-l 127.0.0.1:27042`.
   - **Avoid the interactive `frida-ps`/`frida-ls-devices`/`frida` REPL CLI
     tools under Git Bash on Windows** — they use `prompt_toolkit`, which
     throws `NoConsoleScreenBufferError: Found xterm-256color, while
     expecting a Windows console` because Git Bash's pty isn't a real Win32
     console. Use the plain `frida` **Python library** directly instead
     (`frida.get_usb_device()`, `device.enumerate_processes()`,
     `device.attach(pid)`, `session.create_script(...)`) — fully
     non-interactive, works fine.
   - Confirmed the real app process (`cn.upus.app.upprinting`) was not
     running initially; launched it with
     `adb shell monkey -p cn.upus.app.upprinting -c android.intent.category.LAUNCHER 1`
     (find its true identity via `cat /proc/<pid>/cmdline` — `ps` shows a
     custom process label `Cutting`, not the package name, since the app
     sets `android:process` — don't `grep -i upus` against `ps` output, it
     won't match).
   - **`device.attach(pid)` failed** the moment a script was loaded:
     attempt 1 → `frida.ProcessNotRespondingError: unexpectedly timed out
     trying to sync up with agent`; attempt 2 (retry) →
     `agent connection closed unexpectedly`; attempt 3 → the target PID no
     longer existed at all (`unable to find process with pid <n>`). The real
     app process was killed by the injection attempt itself. Android's
     ActivityManager auto-relaunched a fresh instance afterward (visible in
     `logcat` as a normal `InitActivity`/`MainActivity` boot sequence,
     including the app's own `/dev/ttyS1 open() fd=111` — the stock app
     talking to the serial port normally, confirming it does reach that
     point fine on its own).
   - **This is a strong, consistent signal that the same protection
     mechanism (or a related one) detects Frida's default injection
     footprint and kills the process**, not just a slow-device timeout —
     the "agent connection closed unexpectedly" following immediately after
     a timeout, then the PID vanishing, is the signature of the target
     dying mid-handshake with the injected agent, not merely the network
     link being slow. Plain `frida-server` on the default port (27042) with
     default process/thread naming is trivially fingerprintable (port scan,
     `/proc/<pid>/maps` for `frida-agent`, named threads like
     `gum-js-loop`/`gmain`, or a `ptrace` self-check) — this vendor library
     already does at least one other environment check (see #6/#7/#8 above),
     so an added anti-Frida check is consistent with its general posture.

**Revised conclusion for this session**: both the `app_process` route (dies
after `JNI_OnLoad`'s `class have find` point) and the naive Frida-attach
route (dies during agent injection, before any script code even runs) are
blocked by what looks like deliberate anti-tamper/anti-instrumentation logic
in `libnewcutjni.so`. Two realistic next steps for a future session, in
increasing order of effort:
- **Stealthier Frida**: use `frida-gadget` (linked/injected differently,
  no separate `frida-server` process, no default port, configurable to
  avoid common fingerprints) instead of `frida-server`, or apply known
  anti-anti-Frida measures (rename the binary/process, change the listening
  port, patch out `frida` strings in `frida-server` itself) before
  reattempting the same `getHandshake()` probe script (`probe.js`, saved at
  `hardware-re/cutter-e326-bridge/` — see below) against the real process.
- **Static disassembly**: open `libnewcutjni.so` (`armeabi-v7a` copy) in
  Ghidra/IDA and actually read what runs between the `"qaz"/"class have
  find"` log call (`JNI_OnLoad`, offset `0x160d3` region) and the kill, to
  understand the exact check(s) rather than continuing to infer them from
  black-box behavior. This is slower up front but stops the "change one
  thing, burn a device-restart cycle, learn one bit" loop that both attempts
  above ran into.

The working (but blocked) `app_process` bridge code is preserved as-is in

## Breakthrough (same session, continued)

10. **Root cause of the Frida failure identified and fixed**: it was a
    **Frida client/server version incompatibility with this old Android
    7.1.2 (API 25) device**, not vendor anti-tamper. Diagnostic: attaching
    with Frida 17.15.3 and *no script at all* left the target process stuck
    in a ptrace'd/traced state (`ps` showed `state=t`) rather than crashing
    outright — a classic injection-protocol mismatch symptom, not a
    deliberate kill. Fix: use **Frida 16.0.19 for both the client (`pip
    install "frida==16.0.19"`) and `frida-server` on the device** (matching
    versions). With that pairing, a bare attach completed cleanly with the
    process staying in normal `S` (sleeping) state.
11. **`getHandshake()` now works end-to-end** against the real, running
    `cn.upus.app.upprinting` process (found via `/proc/<pid>/cmdline` — `ps`
    shows a custom process label `Cutting`, not the package name). Built
    `hardware-re/cutter-e326-bridge/agent.js` (Frida RPC script) +
    `frida_bridge.py` (Python driver): attaches once, exposes
    `getHandshake` over the same local-TCP wire protocol plan 001 originally
    specified (`nonce\n` in → hex`\n` out on `127.0.0.1:8654`). Verified
    working via the actual socket interface, not just Frida's message
    channel.
12. **The response is plain ASCII text, not opaque binary**: e.g. nonce
    `123456` → `BD:12,14885604;`. General shape `BD:12,<decimal>;`.
    **Confirmed deterministic** — identical nonce always produces
    byte-identical output across repeated, independent calls. Spot-checked
    nonces `1`, `42`, `123456`, `123457`, `999999999` all produced distinct,
    plausible-looking responses in the same format; the mapping from nonce
    to the trailing number isn't a simple linear formula from the few points
    sampled, but reverse-engineering that formula is unnecessary — this
    bridge is a working oracle for any nonce a real machine will ever send.
    Full detail and setup steps: `hardware-re/cutter-e326-bridge/README.md`.

**Plan 001's core objective — obtain correct handshake responses without
reverse-engineering the RSA scheme — is achieved.** What remains
out-of-scope for this plan (per its original Scope section) and still open:
the actual RCMD serial-protocol client that reads real nonces off
`/dev/ttyS1` and drives a full cut sequence using this bridge, and the
physical UART0 tap for true PC-side control. Both were explicitly deferred
when this plan was written and still are.
