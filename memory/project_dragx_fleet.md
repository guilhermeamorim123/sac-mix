Multi-day hardware/software project: patched Android app "DragX" (fork of vendor `cn.upus.app.upprinting`) for CUTTER_E326 film-cutting kiosks, paired with a FastAPI fleet-management panel (`hardware-re/fleet-panel/` in this vault).

**Production deployment is a SEPARATE, unlinked git repo** — `guilhermeamorim123/dragx-fleet-panel` on GitHub, deployed on Render. It is NOT part of this vault's git tree and does not exist on disk by default each session. To deploy any fleet-panel change: `gh repo clone guilhermeamorim123/dragx-fleet-panel` into the session scratchpad, copy the changed file(s) from `hardware-re/fleet-panel/` over, commit, push — Render auto-deploys on push to `main`. Static APK files also live in that repo's `static/` dir (same copy-commit-push flow).

**CHECKIN_API_KEY** (shared secret for app→panel auth): `e17a2065e4cdd74424b3865df9976d633624ccff40a5422555b166acfcb027bc`. Java sources keep the literal placeholder `__CHECKIN_API_KEY__` (never commit the real value); substitute via `sed` into the scratch-compile copy only.

**Compiling against vendor library classes** (e.g. `com.blankj.utilcode.util.AppUtils`, `com.tencent.mmkv.MMKV`): javac has no jar for these. Fix: write a compile-time-only stub class with matching method signatures (verified against the real decompiled smali first), compile against it, then when copying generated smali into the real decompiled tree, exclude the stub's own class file — only the real vendor smali (already present) stays. Same trick used for `InitActivity.java` earlier in the project.

**Current package strategy**: shipping `com.dragx.app` exclusively (renamed from `cn.upus.app.upprinting.dragx`) to avoid Android's signature-mismatch install failures against old/unknown-keystore builds. Old-package machines get no further updates and need a full manual Remover+reinstall, not an in-place update.

**Self-update mechanism** (shipped v1000008+, `SelfUpdateChecker`/`SelfUpdateActivity`): bypasses the vendor's own `MainActivity.a0()`/`UpdateTipDialog` chain, which silently stops offering an already-seen `(appVersion, binVersion)` pair once `MApp.C` ("forcedUpdate", set from the vendor's real backend — outside our control) is `"1"`. Reuses the existing 3-minute `RegistrationGate` poll instead, hitting the already-built `/v1/api/ver01/app_upgrade`. No dismissal cache — re-prompts every poll until actually updated. **Bootstrap gap**: a machine on a pre-1000008 build has no way to learn about this mechanism except the vendor's own (unreliable) dialog or a manual reinstall — first delivery to any given machine isn't guaranteed.

**Telemetry** (shipped v1000009): app now calls the previously-built-but-never-called `/api/machines/checkin` endpoint every poll, reporting serial + `dragx_version`. Only machines on 1000009+ show up with real data; anything older is invisible to the panel (`dragx_version` stays NULL, `last_seen_at` stays stale — that field is ONLY touched by checkin, not by the older read-only `/status` poll).

**Vendor's Aria-based "Teste de fábrica" install screen** (hidden factory-test menu inside DragX, unrelated to anything built in this project) hardcodes requests to root-level paths `/Remover-Antigo.apk` and `/NovoPacote.apk` on whatever domain is typed — not `/static/...`. Fleet panel now serves those exact paths directly (not a redirect — Aria issues a HEAD probe first, and FastAPI's plain `@app.get` doesn't answer HEAD automatically; must use `@app.api_route(path, methods=["GET","HEAD"])`).

**Vendor's real cut-balance/account system** (`BALAQTY`/`USEQTY`, MMKV-backed, synced from `cutter.skycut.cn`'s `find_user_detail` endpoint via the *unredirected* `.a()` Retrofit client) is a SEPARATE thing from this project's own dashboard `cut_balance` feature (2000 default, auto-replenish, purely informational, no enforcement). The vendor's version can actually block cutting (`FilmCutActivity`: `if (y < 1) { Toast "Insufficient Balance"; return; }`) when a `forced-balance` flag is active — confirmed NOT currently blocking on the one test machine checked (2026-07-20), but the smali here is more convoluted than expected (multiple write sites, an unidentified encoding helper `b.b.a.a.j.a.k()`) — deliberately left unpatched pending deeper investigation with live-device testing. See [[feedback-slow-down-on-risky-vendor-patches]].

**ADB access**: when a machine is reachable by USB, `adb root` works (device is rooted) — full filesystem access, e.g. directly editing `/data/data/<pkg>/shared_prefs/*.xml` to fix stuck local state (used to unstick a machine's `registration_status` and to run `cmd package set-home-activity` when the wrong app became the default launcher after a reinstall). **Recurring gotcha**: every time `com.dragx.app` gets freshly installed (via ADB or via the Remover), the default home app resolves back to whatever OTHER launcher-capable package is still on the device (e.g. the bare vendor `cn.upus.app.upprinting`) — always re-run `adb shell cmd package set-home-activity "com.dragx.app/cn.upus.app.upprinting.dragx.ui.StartActivity"` after any reinstall, don't assume it carries over. **Git Bash / MSYS path-mangling**: `adb shell <cmd> /data/...` and `adb push local /data/...` silently get the leading `/data/...` rewritten into a Windows path (`C:/Program Files/Git/data/...`) by Git Bash's POSIX-path auto-conversion, breaking the command. Prefer `adb install -r <local-windows-path>` (handles push+install in one step, sidesteps the issue) over separate `adb push` + `adb shell pm install`; for other remote-path shell commands, this project hasn't yet found a fully reliable escape (double-leading-slash and `MSYS_NO_PATHCONV=1` each broke a different half of the command) — worth solving properly next time it's needed.

**Vendor's own factory-reset button** (Settings → Restart/Shutdown → "Restore Factory", `RestartShutdownActivity`) was already fully built and working, just gated behind a hardcoded password (`"2323"`) nobody had — patched (v1000010) to `"5656"` instead, a single string-constant swap, same pattern as the test-bypass PIN. Much lower-risk than building new UI, since it reuses the vendor's own already-tested reset logic (`b.b.a.a.l.d.X0(this)`) untouched. **Caveat discovered the same night**: if `com.dragx.app` gets fully uninstalled (e.g. mid-troubleshooting via the Remover) and only the bare vendor app `cn.upus.app.upprinting` remains, the user can end up looking at *that* app's own Settings screen instead — which still has the original, unpatched `"2323"` password and looks identical. Always confirm which package is actually in the foreground (`adb shell dumpsys window | grep mCurrentFocus`, or just check for the DragX branding) before assuming a password patch didn't take effect.

**Self-update install crash marathon (2026-07-21, test machine `6S9OZIVD0N`, Android 7.1.2/API 25 — older than expected, check actual OS per-device rather than assuming from targetSdk)**: got `SelfUpdateActivity`'s "download the new APK and launch the installer" step working end-to-end only after finding and fixing SEVEN distinct, real bugs in sequence — each confirmed live via `adb logcat`, not guessed:
1. Reused the existing `utilcode.fileprovider`'s authority string but only renamed it (old package name → new) — changing a `<provider>` authority *between app versions via an in-place update* breaks FileProvider's metadata lookup system-side (`IllegalArgumentException: Couldn't find meta-data for provider`), even though a **fresh install** with the same corrected manifest works fine. Fix path was to stop reusing that provider entirely for self-update, not to "correctly" rename it.
2. Calling `finish()` on `SelfUpdateActivity` immediately after `startActivity()`-ing the install intent raced with the installer's own activity actually taking the foreground — installer process started, then got silently reclaimed as "empty" with no UI ever shown. Fix: don't finish() there at all.
3. `FLAG_GRANT_READ_URI_PERMISSION` alone intermittently insufficient on this OS — tried explicit `grantUriPermission()` calls as a fix; this was a **dead end** (see below).
4. An unguarded `grantUriPermission()` loop over `queryIntentActivities()` results threw on one candidate and skipped `startActivity()` for the real target entirely — fixed by wrapping each grant attempt individually, but the underlying permission error persisted regardless.
5/6. Root cause of the "does not have permission to uri" family of errors turned out to be **unrelated to grants at all**: reusing the bare `androidx.core.content.FileProvider` class for a *second* `<provider>` entry in the same manifest (the new self-update provider, alongside the pre-existing `cn.upus.app.upprinting.dragx.fileprovider` one) made Android route PackageInstaller's read query to the **wrong registered provider instance** — confirmed via the exact error text naming the *other* authority. Reverting the grant-loop complexity back to the vendor's own simple, already-proven `IntentUtils.getInstallAppIntent()` pattern did NOT fix it by itself; a full device reboot didn't fix it either (ruled out "stale session state" as the cause).
7. **Actual fix**: give the self-update FileProvider its own **distinct Java subclass** (`SelfUpdateFileProvider extends FileProvider`, zero added behavior) instead of sharing a class name with any other provider entry. Confirmed by pattern-matching: every *other* FileProvider already declared in this app's manifest (zbar/QR, AgentWeb, Bugly, blankj-utilcode) already uses its own unique subclass — only the self-update one had skipped that convention. Fixed on the first try once identified (v1000018).

**Takeaway for future FileProvider work in this app**: always give a new `<provider>` a dedicated subclass, never reuse `androidx.core.content.FileProvider` (or any class another provider entry already uses) bare, even for a "quick" fix. Also: `<provider>` authority changes are unsafe to ship as in-place updates — treat any provider-authority rename as effectively requiring a fresh install to take effect cleanly, and prefer adding a new authority over renaming an old one.

**Banner carousel images silently failed to load after the `cn.upus.app.upprinting.dragx` → `com.dragx.app` package rename (found + fixed 2026-07-22)**: `MainActivity.smali`'s banner-carousel fallback (4 branded drawables, `banner_dragx_1..4`, added in an earlier session) referenced them via `android.resource://cn.upus.app.upprinting.dragx/drawable/banner_dragx_N` URIs — hardcoded to the *old* package name from before the rename. The drawables themselves were still correctly present in `res/drawable-xxhdpi/`; only the URI's authority was stale, so `ContentResolver`/Glide silently failed to resolve them (no crash, no log noise — the carousel container rendered, just empty). Symptom matched exactly what the owner reported ("banners estão aqui mas as imagens não aparecem"). Fixed by updating all 4 string literals to `android.resource://com.dragx.app/...` (v1000022) — no Java recompile needed, pure smali string edit + apktool rebuild. **Lesson**: any other hardcoded `cn.upus.app.upprinting.dragx` string literal anywhere in the smali tree (URIs, authorities, intent component names) is a landmine left over from the rename — worth a full-tree grep (`android\.resource://cn\.upus\.app\.upprinting\.dragx`) if any other feature added before the rename starts behaving strangely post-rename.

**Real Android factory reset wipes the WHOLE device, not just app data (2026-07-21, confirmed live)**: `RestartShutdownActivity`'s "Restore Factory" (see above) triggers the genuine OS-level `Settings.ACTION_FACTORY_RESET` flow (Configuração original → REDEFINIR TABLET → APAGAR TUDO, all real system confirmation screens) — this erases every user-installed app (`com.dragx.app` included, since it's sideloaded, not part of the factory system image; only the bare vendor `cn.upus.app.upprinting` survives, whatever was truly baked into the system partition), WiFi credentials, and even the system clock (resets to 1970-01-01, breaking TLS/DNS until corrected). The original project assumption that factory reset would land back on *DragX's own* registration screen was never actually true — it lands on bare stock Android/vendor app, requiring a full DragX reinstall afterward to get back to a usable state. **Fix shipped (v1000019)**: a second hidden gesture, `SecretExitTapListener`, same 7-tap/6s gesture and same PIN (`160172`) as the entry gesture, wired onto `SettingActivity`'s header title (`tv_title`, found via `getResources().getIdentifier` + `findViewById` at the end of `j()`, same technique as the entry gesture) — while already in test-bypass mode, this clears `test_bypass_enabled` + cached `registration_status` and returns to `RegistrationActivity` directly, no OS-level wipe, no reinstall needed. Confirmed working live. Picking a safe anchor view mattered: the first attempt targeted `view1` (an existing invisible spacer at the very bottom screen edge, y≈1180-1208 of a 1208px-tall screen) and never registered taps at all across many attempts (suspected system gesture-exclusion zone on this nav-bar-less hardware); switching to the header title (`tv_title`, y≈29-72, same row as the working back/home buttons) was needed before it worked reliably. **Lesson**: for future secret-tap anchors on vendor screens, prefer elements near the top/header, not the bottom edge.

**Stock `AlertDialog.Builder` two-button panel is unusable on this hardware's narrower screen (found 2026-07-21)**: `setPositiveButton`/`setNegativeButton` mis-measures and squeezes the positive button down to ~18px width (confirmed via live `uiautomator dump`, e.g. `ENTRAR` bounds `[702,504][720,612]`) — effectively untappable. **Fix pattern**: replace the stock two-button panel with a custom `LinearLayout` (vertical) containing manually-added, full-width `Button`s wired with their own `setOnClickListener`, passed via `.setView(container)` instead of `.setPositiveButton()`/`.setNegativeButton()`. Applied to both the test-bypass entry dialog (`RegistrationActivity.showTestBypassDialog()`) and the exit dialog (`SecretExitTapListener.showExitDialog()`) in v1000020. **Not yet applied** to `SelfUpdateActivity`'s "Atualizar agora"/"Depois" dialog, which uses the same vulnerable stock pattern but hasn't been reported broken — revisit if it ever is.

**Registration submission persistent background retry — shipped v1000023 (2026-07-27)**: confirmed live that a customer at a flaky-internet location got the correctly-designed failure Toast ("Não foi possível enviar o cadastro...") on `RegistrationActivity`'s submit, but never manually retried, so the registration silently never reached the panel — happened twice with the same customer in one day. **A THIRD, architecturally different machine category found in the fleet: "Devia Membrane Cutter" (Bluetooth-only, no embedded Android tablet) — investigation opened and paused 2026-07-28**: unlike every other machine this project has touched, this one has no onboard Android head unit at all — just a small status display, controlled entirely by a separate phone app ("Devia") over Bluetooth. This means the entire "install DragX on the machine's own tablet" approach is **not applicable** here; there is nothing to install DragX onto. Any future control of this device requires a standalone client (phone app or similar) speaking its Bluetooth protocol directly — a fundamentally different kind of project from everything else in this fleet.

- Serial observed: `DEVIA202009144JU4AA` — the `202009` segment is very likely a YYYYMM manufacture date code (September 2020), by far the most common convention for this kind of serial; not independently confirmed against a spec sheet.
- Device is **BLE** (Bluetooth Low Energy), not Classic — confirmed by: Windows' standard "Add a device" Classic-discovery flow never saw it (even sitting right next to the PC, while it correctly saw the owner's own phone in the same scan), but it showed up immediately once scanned with a real BLE tool (Microsoft Store's free "Bluetooth LE Explorer", installed via `winget install --id 9N0ZTKF1QD98 --source msstore`). This confirms the untested hypothesis #1 from `BLUETOOTH_INVESTIGATION.md` (which was about a *different* machine, CUTTER_E326's secondary radio) generalizes: these cheap cutter control boards commonly use BLE for their actual control-channel advertising, not Classic SPP, even though Classic PIN-pairing separately succeeded on the CUTTER_E326 investigation — worth trying a real BLE scanner FIRST on any future unknown machine, before assuming Classic.
- Bluetooth name: **`CUTTER_FBFC`** (same `CUTTER_<hex-suffix>` naming convention as CUTTER_E326's own secondary radio — strongly suggests a shared common OEM Bluetooth/BLE module supplier across multiple unrelated cutter brands, not a coincidence). BLE address: `00:15:A6:01:0E:1D` — note the OUI prefix (`00:15:A6`) is one digit off from CUTTER_E326's secondary radio (`00:16:A6:01:75:2B`), reinforcing the shared-chip-vendor theory.
- **Blocked**: connecting from Windows (via Bluetooth LE Explorer) fails every time with "Connection failures — Device unreachable", regardless of whether the phone app is also connected at the time (ruled out "only one connection slot taken by the phone" as the cause — the failure is identical either way). The official Devia iOS app *did* eventually connect successfully to this same machine (after an initial "não é compatível"/"not compatible" message on a first attempt — cause not diagnosed, possibly a stale app state or wrong initial screen, worked on a later attempt), confirming the device itself is NOT faulty — something about Windows' generic BLE central stack/connection-parameter negotiation specifically is what's failing, not the machine.
- **Why this remains unresolved**: getting further requires capturing a real, working Bluetooth session's traffic to read the actual protocol (services/characteristics/command bytes), same conclusion as the CUTTER_E326 Bluetooth investigation reached. Two capture methods were considered this session and both hit a dead end: (1) Android's built-in HCI snoop log — the owner's Android phone broke mid-session, unavailable; (2) iOS's PacketLogger — requires a Mac + Xcode's "Additional Tools", unavailable this session.
- **Best next step identified but not yet executed**: sideload the Devia app onto one of the project's own CUTTER_E326 Android tablets instead of using a personal phone — these already have full root/ADB access established throughout this project, and confirmed real Bluetooth hardware (`android.hardware.bluetooth` + `bluetooth_le` present, per `BLUETOOTH_INVESTIGATION.md`), so HCI snoop logging is directly actionable with zero new dependencies once a CUTTER_E326 unit is physically available again (it wasn't, this session, when this idea came up). Real risk not yet tested: the Devia app (presumably built for modern Android) may refuse to install or run on that tablet's Android 7.1.2 — unknown until tried.
- **Recommendation if a customer has one of these machines and just wants it working today**: keep using the official Devia app — it does work — rather than attempting a custom replacement, until a real protocol capture is actually in hand.

**UPDATE same session (2026-07-28) — a second, independent connection path found: genuine USB, not just Bluetooth.** The machine has three physical ports: a barrel DC power jack, a USB-A **host** port (for the machine to read a USB flash drive itself — confirmed wrong direction for PC control, same "two hosts can't talk" issue diagnosed earlier this session on the other new machine), and critically a **USB-B device port** (the "printer cable" shape) — this one worked:
- Connecting USB-B→PC, Windows enumerated it immediately as a genuine **USB Printer Class device**: `USB\VID_0483&PID_5750\SKYCUT_7A0`. **"SKYCUT"** is the same brand/backend as `cutter.skycut.cn` (the real account/cut-balance system CUTTER_E326's own vendor app already talks to) — confirms this Devia-branded unit is ALSO Skycut-family hardware underneath, same white-label pattern as everything else found this session. VID `0483` is STMicroelectronics' vendor ID (common for STM32-based embedded USB devices), consistent with a small STM32 microcontroller running the cutter's USB stack.
- No `usbprint.sys` class driver was bound (empty `Service` field on the PnP entry), so a direct bidirectional device handle (`CreateFile`/`ReadFile`/`WriteFile`) wasn't available. Worked around this by registering a Windows "Generic / Text Only" printer queue on the auto-created virtual port (`Add-PrinterDriver -Name "Generic / Text Only"`; `Add-Printer -Name "SkycutRaw" -DriverName "Generic / Text Only" -PortName "USB002"`), then sending raw bytes via the classic Win32 spooler API (`OpenPrinter`/`StartDocPrinter` with `pDataType="RAW"`/`WritePrinter`) through a small inline C# helper (`Add-Type`) — this compiles and works fine in PowerShell 5.1, unlike the WinRT/BLE interop attempted earlier (see below), since it's plain Win32, not WinRT.
- Confirmed the write path is genuinely clean: `WritePrinter` returns success and the job leaves the spooler queue immediately (`Get-PrintJob` empty right after — not stuck pending).
- **Tried 5 different safe, non-destructive HPGL-family command strings** (`IN;`, `;`, `OI;`, `ESC.@;`, `ESC%-1B`) one at a time with the owner watching the machine directly for any reaction (light, sound, screen change, motor twitch) — **zero reaction to any of them**. Deliberately avoided any pen-down/movement-style commands given this project's established hardware-caution lesson (see `feedback_hardware_communication_caution.md`) — only tried safe reset/query-class commands.
- **Interpretation**: same "write succeeds, device shows no observable reaction" pattern as DragX's own CUTTER_E326 serial-handshake investigation earlier this same session — writing bytes at the OS/API level succeeding is not evidence the firmware understood or acted on them. Either the real protocol isn't plain-ASCII HPGL despite USB-Printer-Class enumeration, or (more likely, per the missing `usbprint.sys` binding) genuine two-way communication is required and a write-only path can't get anywhere without capturing what a real, working command exchange looks like first.
- **This USB path is likely a substantially easier target than the BLE path** once a real reference capture exists: USB traffic is far easier to capture than BLE (e.g. Wireshark + USBPcap on Windows, no special dongle needed, unlike BLE sniffing) — if the Devia app has ANY desktop/USB mode, or if genuine Skycut PC cutting software exists (worth searching for once resuming this), capturing that traffic while it drives this exact port would very likely reveal the working command set directly.
- **WinRT/BLE PowerShell interop dead ends hit while investigating (for the record, don't retry blindly)**: `[Windows.Devices.Bluetooth.BluetoothDevice]::GetDeviceSelector()` + `DeviceInformation.FindAllAsync` — `.GetResults()` isn't reachable via plain PowerShell COM interop on an `IAsyncOperation`; `DeviceWatcher.Added` — PowerShell 5.1 cannot `Register-ObjectEvent` on WinRT events at all ("O Windows PowerShell não pode assinar eventos Windows RT"); a hand-written C# `Add-Type` await-helper referencing `Windows.Foundation.IAsyncOperation<T>` fails to compile because `Add-Type`'s default compiler can't resolve WinRT projection types without real `.winmd` metadata references, which aren't trivially reachable from `Add-Type`. **Conclusion**: don't attempt raw WinRT/BLE scripting from Windows PowerShell 5.1 again — either use a real tool (Microsoft Store's free "Bluetooth LE Explorer" worked immediately, `winget install --id 9N0ZTKF1QD98 --source msstore`) or move to PowerShell 7+/a compiled .NET project if BLE automation is ever genuinely needed. Plain Win32 API interop via `Add-Type` (no WinRT) works completely fine, as the raw printer-write helper above demonstrates.

    ```
    IN WSJP=6240092912 U<x0>,<y0> D<x1>,<y1> D<x2>,<y2> ... D<xN>,<yN> U<0>,<0> 
    ```
    - `IN` — literal HPGL "Initialize" opcode (space-separated, not `;`-terminated like the identification commands)
    - `WSJP=6240092912` — a **hardcoded literal constant** in the app (not computed/derived from device state) — likely a fixed job-format/protocol-version signature the firmware checks for; safe to reuse verbatim
    - `U<x>,<y>` — HPGL-style "pen up, move to" — used exactly once, for the very first point of the path (the starting corner, moved to without cutting)
